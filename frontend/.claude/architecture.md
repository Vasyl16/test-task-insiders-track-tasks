# Frontend Architecture

## Architecture Style
A pragmatic Feature-Sliced Design: `app / pages / widgets / features / entities / shared`, combined with a centralized API layer under `shared/api` (rather than splitting HTTP code per-feature).

Data flow: Page → `shared/api/services` hook → `shared/api/queries` → `shared/api/axios` instance → backend API.

## Layer Responsibilities
- `app/`: application-wide composition — root `App.tsx`, `providers/` (context/query providers composed once near the root), `routes/` (router config, `ProtectedRoute`/`PublicRoute` guards), `layouts/` (shared page shells, e.g. the authenticated app shell with nav). Nothing here is domain-specific.
- `pages/`: route-level composition, grouped by area (auth, dashboard, workspace, project, task). Pages compose features/widgets/entities — they never call HTTP directly. `pages/dashboard/DashboardPage.tsx` lists the user's workspaces; `pages/workspace/WorkspacePage.tsx` (route: `/workspaces/:workspaceId`) shows one workspace and its projects; `pages/project/ProjectPage.tsx` (route: `/workspaces/:workspaceId/projects/:projectId`) shows one project and its tasks.
- `widgets/`: composite UI blocks made of multiple features/entities. `widgets/app-header` (`ui/AppHeader.tsx`) — the dashboard header, composing the current user's email (`entities/user` data, via `shared/api/services`) with the logout action (`features/auth`'s domain, though the action itself is just `useAuth().logout`). Extracted out of `app/layouts/DashboardLayout.tsx` because it's a composite, not a plain shell. `widgets/task-board` (`ui/TaskBoard.tsx`) — the drag-and-drop Kanban board on `ProjectPage`, composing `entities/task` data with the update/delete actions from `shared/api/services/useTasks`; see the design-system section below for the drag-and-drop details.
- `features/`: one folder per user-facing capability (`auth`, `workspace`, `project`, `task`, `comment`), each owning only its own business logic — components, hooks, schemas (Zod), types, utils. Folders are created lazily. `features/auth` — `schemas/{loginSchema,registerSchema}.ts` (Zod; register's schema adds a client-only `confirmPassword` with a `.refine` check, never sent to the backend) and `components/{LoginForm,RegisterForm}.tsx`. `features/workspace`/`features/project` — one `{name}Schema.ts` shared by `Create{Name}Form.tsx` and `Edit{Name}Form.tsx` each (kept as two components rather than one mode-switched component, matching the `task` pattern below). `features/task` — shares one schema (`taskSchema.ts`) across both `CreateTaskForm.tsx` and `EditTaskForm.tsx` (kept as two separate components rather than one mode-switched component — similar fields, but different defaults and submit copy). `EditTaskForm` was removed and then restored the same session per follow-up feedback — see `progress.md`. Every `Edit*Form` disables its submit button until `formState.isDirty` — there's nothing to save if nothing changed, and this is enforced client-side only (a no-op PATCH would otherwise still round-trip to the backend and succeed). HTTP calls and server-state hooks still live in `shared/api`, not here — a feature folder holds the form/UI logic that *consumes* those hooks.
- `entities/`: domain models shared across features/pages — `entities/user/model/user.ts`, `entities/workspace/model/{workspace.ts,workspace-member.ts}`, `entities/project/model/project.ts`, `entities/task/model/task.ts`. Each is a plain type mirroring the backend's response DTO shape. `entities/task/model/task.ts` also exports `taskStatusValues`/`TASK_STATUS_LABELS` and `taskPriorityValues`/`TASK_PRIORITY_LABELS`/`TASK_PRIORITY_DOT_CLASSES` — defined once here since the Zod schema, the create form, and the Kanban board all need them.
- `shared/api/axios`: the single Axios instance, interceptors (attach access token, handle 401 refresh-and-retry), and the token manager (sole owner of token storage).
- `shared/api/queries`: one file per domain (`auth.ts`, `workspace.ts`, `project.ts`, `task.ts`). Plain HTTP functions only — no React, no query/mutation distinction (e.g. `getMe`, `login`, `register`, `logoutRequest`; `getWorkspaces`, `createWorkspace`, `getWorkspaceMembers`, ...). `project.ts`'s functions all take `workspaceId` first (Projects nested under `/workspaces/:workspaceId/projects`); `task.ts`'s all take `workspaceId` then `projectId` (Tasks nested one level deeper still).
- `shared/api/services`: React Query hooks per domain (`useAuth`, `useLogin`, `useRegister`; `useWorkspaces`/`useWorkspace`/`useWorkspaceMembers`/`useCreateWorkspace`/...; `useProjects`/`useProject`/...; `useTasks`/`useTask`/`useCreateTask`/`useUpdateTask`/`useDeleteTask`) that wrap `queries` for components to consume. Delete mutations pass `exact: true` to their list invalidation and explicitly `removeQueries` the deleted item's own detail key — see the note below on why. `useUpdateTask(workspaceId, projectId)` deliberately takes `id` per mutate-call rather than at hook-creation time (same shape as the delete hooks), so a task list can update any row's status from one shared hook instance instead of calling a hook once per row inside a `.map()` — which the Rules of Hooks disallow.
- `shared/api/queryClient.ts` / `queryKeys.ts`: the shared `QueryClient` instance and cache-key factory, so queries/mutations invalidate consistently.
- `shared/lib`: generic, framework-agnostic helpers with no business logic. First one: `getErrorMessage.ts` (pulls a backend error message out of an Axios error, with a fallback) — kept here rather than in `features/auth` since it isn't auth-specific.
- `shared/ui`: presentation-only primitives with no domain knowledge — `Button.tsx` (`variant: 'primary' | 'ghost' | 'logout' | 'nav'`; `primary` has no baked-in width so it works both full-width, via an explicit `className="w-full"` at the call site, and inline; `nav` is for quiet text actions on the dark desk background, `ghost` for the same on paper), `Input.tsx` (labeled input + error message, `forwardRef` so it works with React Hook Form's `register()`), `Select.tsx` (same labeled treatment as `Input`, for native dropdowns like task status/assignee), `Listbox.tsx` (a fully custom dropdown — not a styled native `<select>` — for cases wanting a richer trigger/panel, e.g. a colored dot per option; generic `options: {value, label, dotClassName}[]` shape carries no domain knowledge, wired into forms via React Hook Form's `Controller` rather than `register()` since it isn't a native form element), `FormError.tsx` (form-level error line), `Modal.tsx` (portal-rendered dialog — see the design system section below). Used by `features/auth`/`features/workspace`/`features/project`/`features/task`'s forms and `widgets/app-header`.
- `shared/hooks`, `shared/utils`, `shared/constants`: not created yet, same rule — created as content actually exists.
- `store/` (root-level, not yet created): client-only global UI state (theme, sidebar, modal visibility). Server state always stays in the query layer via `shared/api/services`, never mirrored here.

## Module Structure
Folders are created as they're needed, not scaffolded empty ahead of time. `widgets/` holds `app-header`; `features/` holds `auth`, `workspace`, `project`, `task`; `entities/` holds `user`, `workspace`, `project`, `task`; `shared/` has `api/`, `lib/`, `ui/`. See `CLAUDE.md` for the full target tree.

## Why This Structure
- Centralizing `queries`/`services`/`axios` under `shared/api` (instead of duplicating an API slice per feature) keeps token handling, cache keys, and the Axios instance in one place — there's exactly one place to look for "how does this app talk to the backend."
- `entities` vs `features` split keeps domain data shape (`User`, `Workspace`, `Project`) separate from the UI/business logic that manipulates it, without forcing an API layer per feature.
- Matches the backend's domain split (auth, workspace, project, task, comment) so the two codebases stay easy to reason about together.
- A single Axios instance + interceptor pair keeps token handling (attach, refresh, retry) in one place instead of scattered per-request.

## API Integration
- Base URL and any environment-specific config should come from Vite env vars (`import.meta.env`), not hardcoded.
- Auth endpoints: `POST /api/auth/{register,login,refresh,logout}`, `GET /api/auth/me`.
- Workspace endpoints: `GET/POST /api/workspaces`, `GET/PATCH/DELETE /api/workspaces/:id`, `GET /api/workspaces/:id/members` (used for the task assignee dropdown; `POST /api/workspaces/:id/members` — invite — still has no frontend, deliberately deferred).
- Project endpoints: `GET/POST /api/workspaces/:workspaceId/projects`, `GET/PATCH/DELETE /api/workspaces/:workspaceId/projects/:id`.
- Task endpoints: `GET/POST /api/workspaces/:workspaceId/projects/:projectId/tasks`, `GET/PATCH/DELETE /api/workspaces/:workspaceId/projects/:projectId/tasks/:id`.
- See `backend/.claude/progress.md` for exact request/response contracts.
- CORS is already enabled backend-side for the Vite dev origin (`http://localhost:5173` by default, via `CORS_ORIGIN`).

## A TanStack Query gotcha worth remembering
`invalidateQueries({ queryKey: [...] })` fuzzy-matches by key **prefix** by default — invalidating `['workspaces']` also matches (and refetches) `['workspaces', id]` and anything nested under it. This is usually fine, but it actively caused a bug: deleting a workspace while its own detail page was still mounted triggered a refetch of that same now-deleted workspace's detail/projects queries, producing spurious 404s. Fixed by (a) passing `exact: true` on delete mutations' list invalidation plus an explicit `removeQueries` for the specific deleted id, and (b) navigating away *before* firing the delete mutation (not after awaiting it) so the page's queries unmount before the mutation's `onSuccess` cache operations run. Either alone wasn't enough — a still-mounted query observer refetches even after its cache entry is removed.

## Visual Design System — "The Ledger Desk"
Built via the `frontend-design` skill (`.claude/skills/frontend-design/`). Subject: workspaces are ledgers, projects are entries logged inside them.
- **Tokens** live in `src/index.css` as a Tailwind v4 `@theme` block — colors (`desk`, `desk-raised`, `paper`, `paper-dim`, `ink`, `brass`/`brass-light`/`brass-deep`, `oxblood`, `fog`, `moss`) and fonts (`--font-display`: Fraunces, `--font-body`: IBM Plex Sans, `--font-mono`: IBM Plex Mono, loaded via Google Fonts in `index.html`). Any component can use them as ordinary Tailwind utilities (`bg-desk`, `font-display`, etc.) — no separate theming layer. `moss` is the one color added purely for a semantic signal (task priority), not the brand palette itself — see the priority note below.
- **Canvas vs surface**: `bg-desk` (dark ink-navy) is the page background everywhere (`AuthLayout`, `DashboardLayout`); `bg-paper` (warm parchment) is reserved for cards, the auth form, and modals. Don't invert this — a full-bleed paper background was explicitly avoided as one of the "generic AI design" defaults called out by the skill.
- **Signature element**: a small brass corner tab (`absolute -top-2.5 left-* h-5 w-9 rounded-b-sm bg-brass`), repeated on workspace cards, the auth card, and every `Modal`. It's the one deliberately-bold, memorable device — everything else stays quiet, per the skill's restraint principle.
- **Button variants map to background context**, not just visual weight: `primary` (brass fill) works on both paper and desk; `ghost` (quiet ink text) is for on-**paper** contexts (e.g. inside a modal); `nav` (quiet fog text) is for on-**desk** contexts (the header). Using `ghost` directly on `bg-desk` was a real contrast bug caught via screenshot review — that's why `nav` exists as a separate variant instead of a `className` override.
- **Ledger entry numbers must be honest**: anywhere a list is numbered (projects in `WorkspacePage`), the number must reflect genuine chronological order (oldest = `01`), even if the API returns newest-first — reverse the array at the display layer rather than numbering in received order. A numbered marker that doesn't track a real sequence reads as decorative, which the skill explicitly warns against. Tasks used to follow this too, but the numbering was **removed** when tasks moved to the Kanban board (`widgets/task-board`) — once a list splits into three status columns, a running number no longer encodes a real sequence, so keeping it would itself become the decorative violation the rule warns against.
- **Motion**: `motion-safe:animate-[...]` (not bare `animate-`) on all entrance animations, so `prefers-reduced-motion` users get no animation, not a lesser one.
- When extending this system to new pages, reuse the existing tokens/variants rather than introducing new colors — check `Button`/`Input`/`Select`/`Modal` first before writing new Tailwind classes from scratch. The Task UI reused every primitive as-is; the only true addition was `Select` (a `<select>` didn't fit `Input`'s API), styled to match `Input` exactly rather than inventing a new look.
- **Status/state as typography, not new colors**: a `DONE` task is shown with `line-through opacity-50` on its title rather than a colored badge — the existing palette (paper/ink/brass/oxblood/fog) covers surfaces and actions; task status is a *reading* affordance, not another accent color to introduce.
- **Task priority is the deliberate exception to "no new colors"**: `TASK_PRIORITY_DOT_CLASSES`/`TASK_PRIORITY_BORDER_CLASSES` (`entities/task/model/task.ts`) map `LOW`/`MEDIUM`/`HIGH` to `moss`/`brass`/`oxblood` — genuine traffic-light green/amber/red, not palette-matched brand tones. A priority indicator has to be scannable at a glance across a board, which is a different job than the rest of the UI's quiet, coherent-with-itself color use; `moss` is the *only* net-new color introduced for it (medium/high deliberately reuse existing tokens instead of adding two more). On the Kanban card, priority renders as a `border-t-4` on the card itself (not a dot) plus a plain-text label (`"High · assignee@example.com"`) — color alone isn't an accessible signal, so the text carries the same information for anyone who can't distinguish the border color.
- **Custom vs native form controls**: default to a native `<select>` (`shared/ui/Select.tsx`) unless there's a specific reason for a fully custom dropdown (`shared/ui/Listbox.tsx`) — natives are simpler, need no `Controller` wiring, and get keyboard/screen-reader support for free. `Listbox` exists specifically because the priority picker needed a richer visual (colored dot per option, custom open/close animation) that a native `<select>` can't provide for its option list. The task assignee picker (`CreateTaskForm`/`EditTaskForm`) was moved from `Select` to `Listbox` per explicit feedback, even though it has no dot/color to show (`dotClassName` is simply omitted per option) — requested purely for the richer trigger/panel look to match priority, not for any accessibility or data reason. Don't reach for `Listbox` by default just because it's available; status (`Select`) stayed native since nobody asked otherwise.
- **`Listbox` inside `Modal`, an Escape-key gotcha**: both close on Escape via their own `document`-level `keydown` listener. If `Listbox`'s listener is a normal bubble-phase listener (the default), pressing Escape to close an *open* listbox also closes the *whole modal* underneath it — two independent listeners on the same `document` target both fire, `Listbox` closing itself doesn't stop `Modal`'s handler from also running. `Listbox` registers its listener on the **capture** phase and calls `event.stopPropagation()` in the Escape branch specifically to prevent this — a capture-phase listener on `document` runs before an event dispatched on a descendant element even reaches `document`'s bubble-phase listeners, so stopping propagation there pre-empts `Modal`'s handler entirely. Any future `document`-level Escape/keydown listener nested inside `Modal` needs the same capture+stopPropagation treatment, or it'll have this same bug.
- **Kanban board (`widgets/task-board/ui/TaskBoard.tsx`)**: drag-and-drop uses **DnD Kit** (`@dnd-kit/core`), replacing an earlier native HTML5 DnD implementation — see the dedicated "Drag-and-drop: DnD Kit" section below for the full rationale and lifecycle. An inline status `<select>` existed on each card early on as an accessible fallback (native drag-and-drop alone excludes keyboard and screen-reader users), but it was deliberately removed per explicit feedback the same session — status now changes only by dragging (or via the Status field inside the Edit modal below); DnD Kit's `KeyboardSensor` restores *some* of that lost accessibility (a focused, keyboard-activated card can be moved with arrow keys), though it's not a full replacement for the old `<select>`. Every card also has an `Edit` action (opens `EditTaskForm` in a `Modal`, visible to every workspace member) alongside `Remove` (creator-or-owner only) — `Edit` was briefly removed and then restored the same session per further feedback, see `progress.md`. Columns use `bg-desk-raised` (a token defined early but unused until the board existed) so cards (`bg-paper`) read as index cards laid on a slightly-raised tray, one layer between the page's `bg-desk` and the card surfaces.

## Drag-and-drop: DnD Kit
`widgets/task-board/ui/TaskBoard.tsx` uses `@dnd-kit/core` (only — not `@dnd-kit/sortable` or `@dnd-kit/utilities`, see below) in place of the original native HTML5 Drag & Drop API (`draggable`/`onDragStart`/`onDragOver`/`onDrop`/`dataTransfer`). Both are (or were) genuinely dependency-light choices for *this specific requirement* — moving a whole card between columns, no within-column reordering — but DnD Kit was chosen this time because it was explicitly requested, and because it fixes real limitations native DnD had here: pointer-events-based (works the same on touch, where native HTML5 DnD is inconsistent across mobile browsers), has a built-in `KeyboardSensor` (arrow-key dragging for a focused card — native DnD has no keyboard story at all), and separates "what's being dragged" from imperative browser APIs (`event.dataTransfer`) into a declarative `DndContext`/hooks model that's easier to reason about and extend.
- **`DndContext`** (wraps the whole board): the single source of truth for an in-progress drag. Takes `sensors` (below), `collisionDetection={closestCenter}` (compares the dragged card's center point to each droppable column's center — the right choice here since columns are large, non-overlapping regions; `closestCenter` is DnD Kit's simplest/cheapest algorithm and doesn't need anything more elaborate for three side-by-side columns), and the three lifecycle callbacks (`onDragStart`, `onDragEnd`, `onDragCancel`).
- **Sensors** — `PointerSensor` with `activationConstraint: { distance: 8 }` (a drag only "activates" after the pointer moves 8px from its down position; without this, pressing down on a card to reach its `Edit`/`Remove` buttons would immediately be interpreted as a drag attempt, since `listeners` are spread across the whole card) and `KeyboardSensor` (no custom `coordinateGetter` — DnD Kit's built-in default is sufficient for a non-sortable, droppable-based board like this one; a custom `sortableKeyboardCoordinates` getter only matters for `@dnd-kit/sortable`'s within-list reordering, which this board doesn't do).
- **`useDroppable({ id: status })`** (one call per `TaskColumn`, a real function component so each gets its own hook instance — same Rules-of-Hooks reasoning already documented for `useUpdateTask`/`useDeleteTask` not being callable once per row inside `.map()`): the droppable `id` **is** the `TaskStatus` itself, so `onDragEnd`'s `over.id` can be read straight back as the destination status with no separate id→status lookup table. Returns `setNodeRef` (attach to the column's container) and `isOver` (true while a dragged card is hovering this column) — `isOver` directly replaces the old native-DnD implementation's manually-tracked `dragOverStatus` state for the `ring-2 ring-brass` highlight; one less piece of state to keep in sync with the library.
- **`useDroppable`'s sibling, `useDraggable({ id: task.id })`** (one call per `TaskCard`, same per-component-instance reasoning): returns `attributes`/`listeners` (spread onto the card's root div — these wire up the actual pointer/keyboard event handling) and `isDragging` (true only for the card actually being picked up), which replaces the old `draggedTaskId === task.id` comparison against a separately-lifted `draggedTaskId` state — again, state DnD Kit already tracks internally, not duplicated in the widget.
- **`DragOverlay`**: renders a floating clone of the dragged card that follows the pointer, positioned by DnD Kit itself (portal-rendered, outside the normal layout flow) — this is what gives the drag a polished "lifted card" feel instead of the browser's default drag ghost image. The card actually sitting in its column just fades to `opacity-40` (via `isDragging`) and stays in place; it does **not** also receive a `transform` to follow the pointer, since that would fight visually with the overlay clone doing the same job. This requires exactly one piece of board-level state, `activeTask` (the full `Task` being dragged, set in `onDragStart`/cleared in `onDragEnd`/`onDragCancel`) — `DragOverlay` is a portal at the `DndContext` level, so it needs the board to tell it *what* to render; there's no way around holding that much state. Both `TaskCard`'s in-column render and `DragOverlay`'s floating render share the same `TaskCardContent` presentational component, so the two visuals can't drift out of sync with each other.
- **Drag lifecycle**: `onDragStart` looks up the full `Task` by `event.active.id` and stores it as `activeTask` (for `DragOverlay`). `onDragEnd` clears `activeTask`, then reads `event.over` — if the pointer wasn't released over any registered droppable, `over` is `null` and nothing happens (card snaps back to its column, no request fires); otherwise `over.id` is the destination `TaskStatus`. If that matches the task's current status (dropped back in the same column), it's a no-op — no request fires, matching the "ignore drops into the same status" requirement exactly. Otherwise it calls the **same existing** `useUpdateTask(workspaceId, projectId).mutate({ id: task.id, status: destinationStatus })` used before this migration — TanStack Query's cache invalidation, the backend endpoint, and the permission model are all completely unchanged; DnD Kit only replaced how the *drop* is detected, not what happens after it.
- **Why not `@dnd-kit/sortable`**: that package's `useSortable`/`SortableContext` add drag-to-reorder-*within*-a-list, animating other items out of the way as you drag past them. The `Task` model has no persisted ordering field — cards are always shown oldest-first by `createdAt` (chronological, per this design system's "honest ledger number" rule) — so a sortable board would let a user visually reorder cards in a way that snaps back to chronological order the moment the list refetches, which is a regression, not an improvement. Plain `useDraggable`/`useDroppable` (cross-container movement only, no in-list reordering) matches what the data actually supports. If a real manual-ordering feature is ever added (a persisted `order`/`position` column), swapping in `@dnd-kit/sortable` for the within-column reordering piece is a localized change to this one widget, not a rearchitecture — `DndContext`, the sensors, and `onDragEnd`'s status-update branch would all stay as they are.
- **Why not `@dnd-kit/utilities`**: its main export, the `CSS` helper, exists to turn a `transform`/`transition` object into a style string — needed when you apply DnD Kit's `transform` directly to the dragged element itself. Since this board's dragged element doesn't move (only fades; `DragOverlay` does all the visual movement, see above), there's no `transform` to stringify, so the package would sit unused. Add it back if a future change starts applying `transform` to `TaskCard` directly (e.g. dropping `DragOverlay` in favor of the simpler "the element itself follows the pointer" pattern).
