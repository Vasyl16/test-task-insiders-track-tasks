- **V1 Auth UI — Step 2 correction: auth is server state, not Zustand state.**
  - Reversed the Zustand-holds-`user` design from the previous entry after discussion. Settled principle: TanStack Query owns *all* server state, including the authenticated user — a single `["auth","me"]` query is the one source of truth. Zustand is reserved strictly for client/UI-only state (theme, sidebar, modals, etc.) and currently has **no store at all**, since no such UI state exists yet. `zustand` stays installed (it's confirmed as part of the intended stack for that future need), but `store/authStore.ts` was deleted.
  - `api/queries/authQueries.ts`: plain `getMe()` — no React, no hook, just the HTTP call.
  - `api/mutations/authMutations.ts`: plain `logoutRequest()` — calls `POST /auth/logout` with the stored refresh token, swallows its own network errors (logout must succeed client-side regardless of whether the server call does).
  - `api/services/useAuth.ts`: the real hook. `useQuery(['auth','me'], getMe, { enabled: Boolean(tokenManager.getAccessToken()), retry: false })` plus a `useMutation(logoutRequest)` whose `onSuccess` clears tokens and updates the cache. Exposes `user`, `isAuthenticated: Boolean(user)`, `isLoading`, `isError`, `logout`.
  - Deleted `hooks/useAuth.ts`, `store/authStore.ts`, and the `useEffect`/`hydrate()` bootstrap in `App.tsx` — none of that manual wiring is needed anymore; `useQuery` fetches automatically the first time `useAuth()` renders anywhere.
  - `queryKeys.ts` has `auth.me` again.
  - **Real bug found and fixed during verification, not just a design choice:** the logout `onSuccess` originally called `queryClient.removeQueries({ queryKey: queryKeys.auth.me })`. This actually cleared the cache correctly, but — confirmed via console instrumentation in a real browser — did **not** trigger a re-render of already-mounted `useQuery` observers (`ProtectedRoute` stayed on `/dashboard` after logout, tokens were cleared, but nothing reacted). Switching to `queryClient.setQueryData(queryKeys.auth.me, null)` fixed it immediately and reliably — a direct cache write does notify observers, where `removeQueries` apparently doesn't (at least not reliably, on this `@tanstack/react-query` 5.101.2 / React 19.2 combination). This is now the pattern to reuse for the login/register flow too: after storing tokens, call `queryClient.setQueryData(queryKeys.auth.me, user)` directly (register's response already includes the user; login will need one `getMe()` call first) rather than `invalidateQueries`/`removeQueries`.
  - Verified end-to-end in a real browser against the live backend, with two separate browser contexts (learned from an earlier test mistake — `addInitScript` re-seeds on every navigation in the same context, which had made an earlier logout check look broken when it wasn't): registering + visiting `/dashboard` with a valid token renders correctly with the right email; clicking "Log out" clears tokens **and** correctly redirects to `/login` in the same session (no reload); a fresh context with no token at all correctly redirects `/dashboard` → `/login`. Re-ran the original four-route navigation check too — still clean. No console/page errors in any case.
  - Follow-up rename: `api/queries/auth.queries.ts` → `authQueries.ts` and `api/mutations/auth.mutations.ts` → `authMutations.ts` (dot-case → camelCase), to match the naming already used for `useAuth.ts`, `queryClient.ts`, `queryKeys.ts`. Rebuilt/linted clean after.
