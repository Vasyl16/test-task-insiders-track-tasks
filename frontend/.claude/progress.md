- **Bug fix: stale/cross-account query cache surviving logout.** Reported directly: log out, then log in (as a different, brand-new account) in the same tab, and the dashboard briefly/persistently showed the *previous* account's workspaces. Root cause: `shared/api/queryClient.ts`'s `QueryClient` is one in-memory instance for the whole SPA session — `useAuth`'s `logout` `onSuccess` only ever reset the single `auth.me` query to `null`, never touched anything else, so every other cached query (`workspaces.list`, `projects.list`, `tasks.list`, `invites.mine`, ...) survived the logout untouched and got served straight to whichever account logged in next in that tab, since none of those query keys are scoped by user id.
  - Fix: `logout`'s `onSuccess` now calls `queryClient.clear()` to wipe every cached query, **after** the existing `setQueryData(queryKeys.auth.me, null)` call, not before. Order matters and was verified the hard way: `clear()` first (my first attempt) silently broke the logout redirect entirely — `ProtectedRoute` never navigated to `/login`, because `clear()` destroys the `auth.me` query's own cache entry before the explicit `null` write can notify the still-mounted `useAuth()` observer (the same "`removeQueries` doesn't reliably notify observers, `setQueryData` does" behavior this codebase already had documented, apparently also true of `clear()`). Reordering to `setQueryData` first, `clear()` second fixed both problems at once: the redirect fires immediately off the explicit write, and the full-cache wipe happens right after so the next login starts from nothing.
  - Verified end-to-end in a real headless browser, one single tab/session throughout (the bug only reproduces within one `QueryClient` instance, not across fresh tabs): registered User A, created a workspace, logged out (confirmed the redirect to `/login` still fires immediately), registered a brand-new User B in the same tab — B's dashboard correctly shows their own empty state, with zero trace of A's workspace. Zero console errors. `tsc -b`, `npm run lint`, `npm run build` all clean. Test accounts cleaned up afterward.

- **Bug fix: editing a comment with no changes still fired a PATCH.** Reported directly. `CommentSection.tsx`'s `CommentItem` holds its edit draft via a plain `useState` (not React Hook Form, unlike every `Edit*Form` in the app), and its "Save" button was only disabled on `isSaving || draft.trim().length === 0` — nothing compared `draft` against the original `comment.content`, so clicking Edit then Save with zero changes fired a needless `updateComment` mutation.

  - **Audited the rest of the app for the same gap** (dispatched as a subagent, read-only): `EditTaskForm`/`EditWorkspaceForm`/`EditProjectForm` all correctly gate on React Hook Form's `formState.isDirty` already — no bug there. The Kanban board's drag-and-drop (the one other place a value change fires a mutation with no explicit Save button) already no-ops a same-column drop before calling `updateTask.mutate` (`TaskBoard.tsx`'s `handleDragEnd`). `CommentSection.tsx`'s `CommentItem` was the only real instance of this bug pattern in the codebase.
  - Verified end-to-end in a real headless browser: opened a comment's Edit mode with no changes — Save button confirmed `disabled` via `isDisabled()`, not just visually greyed; typed a real change — Save became enabled; reverted the text back to the original — Save correctly went back to disabled. Zero PATCH requests to `/comments/...` fired at any point in the check (Save was never actually clickable while unchanged). Zero console errors. `tsc -b`, `npm run lint`, `npm run build` all clean.
